# AI 前端开发约束规范

## 文档目的与适用范围

本规范用于约束 AI 辅助前端开发行为，确保生成代码符合项目架构、保持代码一致性、避免重复实现、降低维护成本，并保证安全性和性能。

适用于本项目所有前端页面、组件、样式、接口调用与工具函数。技术栈沿用 Vue 3 + TypeScript + Vite + Element Plus；不得因示例出现 Pinia、Axios 等工具而自行引入依赖。用户当前明确要求优先。

AI 生成代码必须经过人工审核，不允许未经检查直接合并到生产环境。本文件位于 `docs/AI-前端开发约束规范.md`，统一维护 AI 开发约束与项目 UI 实施标准。

## 一、AI 开发基本原则

### 1.1 职责边界

AI 可以编写重复性代码、创建组件、生成接口调用、编写工具函数、优化已有代码和编写测试。

AI 不得自行决定项目架构、引入新的技术栈、修改核心设计或进行大规模重构。涉及这些变更时，必须先分析问题、提出方案并取得明确确认。

### 1.2 优先理解已有代码

修改前必须完成以下工作：

1. 从 `FILE_INDEX.md` 定位相关文件并阅读实际代码。
2. 理解当前数据流、状态归属及错误处理方式。
3. 查找已有组件、工具函数、接口方法与类型定义。
4. 确认是否存在类似实现，优先复用。

禁止看到需求后直接创建新文件、重复实现已有功能。

## 二、AI 任务输入规范

需求至少应说明项目技术栈、目标功能、涉及文件、限制条件、已有代码结构及预期结果。仓库中可确认的信息由 AI 阅读代码补充；影响结果的歧义须先澄清。

示例：

```text
项目：Vue 3 + TypeScript + Vite + Element Plus
需求：增加用户列表页面
涉及文件：既有用户页面、UserTable 组件及 src/api/user.ts
要求：复用已有 UserTable；接口通过 API 层调用；支持分页；不修改权限逻辑
已有结构：页面、组件、API 调用与类型定义分别维护
预期结果：列表可加载、分页及展示加载状态，错误处理遵循项目约定
```

示例中的路径与组件仅用于说明需求格式，实施前必须确认其实际存在。

## 三、AI 代码生成规则

单个代码文件建议少于 300 行，超过 500 行必须按职责拆分。不要仅为满足行数机械切割逻辑，也不要将多个独立功能集中在一个文件。

拆分方向：页面组件、业务组件、组合式函数（hooks）、工具函数（utils）及类型定义（types）。目录和命名沿用已有项目结构，不为每次任务新建一套分层。

## 四、组件生成规范

### 4.1 单一职责

页面负责组织业务流程，搜索、表格、表单及可复用业务逻辑按职责拆分。禁止在一个页面中集中实现搜索、列表、编辑、权限、导出及数据处理等全部细节。

同一业务模块下的独立管理功能使用独立 `.vue` 页面并配置对应路由；共用布局、组件和公共逻辑可以复用。

### 4.2 组件说明

创建组件时，必须在实现说明中交代以下内容，不要求向源码添加重复注释：

```text
组件用途：解决的具体展示或交互问题
输入：props、插槽或其他输入
输出：渲染内容、事件及必要的暴露方法
依赖：已有组件、API 方法或组合式函数
是否可复用：是或否，并说明适用范围
```

## 五、状态管理约束

默认使用组件内部状态。弹窗显示、表单输入、loading 和当前页面交互状态属于组件或对应组合式函数，不得随意放入全局 Store。

全局 Store 仅保存用户信息、权限、主题、语言及全局配置等跨页面状态。不得为局部状态新增 Store，也不得自行引入状态管理库。

## 六、接口开发约束

页面和业务组件不得直接调用 `axios.get()`、`fetch()` 等 HTTP 方法。调用链必须遵循：

```text
页面 / 业务组件 → API 层 → 请求封装 → 后端
```

新增接口调用前检查已有接口文件、请求方法、类型定义及错误处理，禁止重复创建。本项目请求封装位于 `frontend/src/api/http.ts`，业务接口位于 `frontend/src/api/`，共用接口类型位于 `frontend/src/types/api.ts`。

请求失败必须终止当前操作并恢复对应状态。禁止自行加入默认值、备用数据源、降级路径或吞掉异常后继续执行等兜底逻辑；确需兜底时，先说明触发条件、行为及影响，取得用户明确同意后再实现。请求错误的展示与状态管理遵循附录。

## 七、TypeScript 约束

禁止使用 `any`。对象、接口响应、组件输入输出及业务状态须具有明确类型；外部未知数据使用 `unknown` 并经过类型收窄或校验后使用。

禁止以无类型的空对象承载配置并逐步扩散隐式类型。配置及业务数据使用明确的 `interface` 或 `type`；沿用已有类型定义，避免重复声明。

```ts
interface UserData {
  id: number;
  name: string;
}

interface Config {
  pageSize: number;
}

const config: Config = { pageSize: 20 };
```

## 八、代码质量约束

- 相同业务逻辑出现两次时，抽取到合适的工具函数、组合式函数或组件，避免重复维护。
- 业务状态、协议值及具有业务含义的数字使用具名常量或枚举，禁止使用含义不明的魔法数字。
- 注释解释必要的设计原因、业务限制或兼容原因，不重复代码已表达的含义。
- 保持修改聚焦任务，遵循已有风格，避免无关优化或提前引入复杂分层。

## 九、UI 开发约束

AI 不得随意设计 UI 风格。必须复用已有组件库、颜色体系、间距、字体、布局及交互约定；不得自行设计按钮颜色、引入 UI 库或增加主题。

页面设计按以下顺序执行：

1. 确定页面结构和数据流。
2. 确定组件拆分及可复用实现。
3. 按已有规范实现代码。

禁止未经上述分析直接生成完整页面。具体视觉、布局、桌面适用范围及错误反馈标准见附录。窗口适配须遵循本项目桌面范围，不能以通用响应式检查为由自行加入移动端或中、小窗口适配。

### 9.1 最小必要信息原则

所有页面、弹窗、表格、表单、tooltip、消息和导出展示均须服务于明确的用户任务。禁止展示无业务价值、重复、与当前任务无关或用户无需关注的内部实现信息。此原则关注信息是否必要，不以元素数量少或视觉留白多作为合规依据。

- 新增字段、说明、状态、统计或操作入口前，必须说明它帮助哪类用户理解什么状态、作出什么判断或完成什么操作；无法说明具体用途的内容不得添加，修改范围内已有的无用内容应删除。
- 页面按业务语义选择并组织内容，禁止因接口返回了字段就逐项展示，或直接铺出完整 JSON、内部配置、协议术语、调试信息及技术中间过程。
- 核心结果、影响范围、必要状态、校验要求和危险操作确认信息保持可见；加载、失败、空数据及未完成状态必须如实区分，不得以精简为由隐藏失败、掩盖风险或伪造成功。
- 有实际用途但低频查阅的明细、原始业务证据和高级选项按需展示，复用附录中的展开详情模式；没有实际用途的内容直接删除，不得仅移入折叠区或 tooltip。运维对象的路径、命令和日志等如属于判断或核对所必需的业务证据，可以在有权限的详情中保留，不得与应用内部调试信息混淆。
- 文案简短、具体，沿用用户熟悉的业务语言；禁止重复标题、显而易见的操作说明、装饰性欢迎语、无行动价值的提示，以及同一结果在消息、状态条和正文中的无必要重复。
- 错误展示严格遵循附录“错误提示与状态管理”：请求错误仍统一显示“系统异常”，不展示或改写后端错误详情，不据此推断原因或提供建议操作；本地校验和业务状态提示只保留必要内容，不得自行增加失败兜底。
- 精简可见内容时保留字段标签、可访问名称、键盘焦点及必要操作入口；接口中供程序使用的标识符、分页和状态字段不必向用户展示。发现无消费用途的响应字段时，应联动后端审核契约，不能以页面隐藏代替服务端的数据过滤或权限控制。

## 十、AI 修改代码流程

1. 说明修改目标。
2. 分析影响范围、可能风险及涉及文件。
3. 执行聚焦目标的小步修改。
4. 检查类型、Lint、相关测试及运行效果，修复发现的问题。

检查前确认项目实际提供的脚本和工具，不假定 Lint、测试工具已经配置。纯文档改动检查内容、路径、命令及 Markdown 结构即可；未执行或无法执行的检查必须如实说明。

## 十一、AI 重构规范

禁止仅以“优化代码”为由直接全部重写。重构须先分析具体问题、提出方案、确认方案，再逐步修改并验证。

常规任务中的局部修改和复用按已授权范围执行；超出任务目标的架构调整、核心设计变更或大规模重构须取得明确确认。

## 十二、安全规范

- 禁止在前端硬编码密钥、令牌、密码等敏感信息。
- 禁止通过日志输出用户资料、凭据或其他敏感数据。
- 禁止使用 `eval()` 等方式直接执行不可信输入。
- 用户输入、接口数据及动态展示内容必须按实际使用场景校验；避免通过 `v-html` 等入口直接渲染不可信 HTML，检查 XSS 风险。
- 保留既有权限、表单校验、凭据处理及危险操作确认逻辑。

## 十三、AI 代码审核清单

### 架构

- [ ] 符合项目目录、职责划分及既有数据流。
- [ ] 已复用已有组件、工具、接口和类型。
- [ ] 额外依赖有必要用途并在授权范围内。

### 代码

- [ ] 符合 TypeScript 规范，无 `any` 或隐式类型扩散。
- [ ] 无重复逻辑、魔法数字及无意义注释。
- [ ] 文件长度符合要求，组件和业务逻辑职责清晰。
- [ ] 状态归属正确，请求通过 API 层及统一请求封装。

### UI

- [ ] 符合附录中的设计规范，复用已有组件和样式。
- [ ] 按项目桌面范围验证布局、滚动及操作可达性。
- [ ] 所有列表页均支持分页，并提供每页 10、20、50 条的数量选择。
- [ ] 已检查加载、空数据、错误、保存中及长内容状态。
- [ ] 保留键盘操作、可见焦点、标签及颜色对比度。
- [ ] 展开详情入口在默认状态下可识别为控件，具备状态箭头、展开/收起文案及正确的可访问状态。
- [ ] 每项展示内容均有明确用户用途，无无用字段、内部实现信息、重复文案或无意义统计。
- [ ] 核心结果、必要状态和风险保持可见；低频有效详情按需展开，无用内容已删除，可访问性未受损。

### 安全与验证

- [ ] 无敏感信息硬编码或日志泄露。
- [ ] 已检查 XSS 风险并正确处理用户输入。
- [ ] 已执行适用的类型检查、Lint、测试和运行验证，明确记录未执行项。
- [ ] 代码交由人工审核，合并与提交须遵循授权范围。

## 十四、推荐 AI 开发流程

```text
需求分析 → 查看项目结构与相关代码 → 制定方案 → 确认方案
→ 生成代码 → 运行检查 → 修复问题 → 人工审核 → 按授权提交代码
```

方案确认依据任务授权范围执行；需要确认的重构或架构变更先取得用户同意。不得在未经明确要求时自行提交、推送或合并代码。本地验证用测试文件遵循仓库约定，不得暂存或提交。

## 十五、推荐 AI 提示词模板

### 功能开发

```text
你是一名前端工程师。
项目技术栈：Vue 3 + TypeScript + Vite + Element Plus
请遵守：
1. 不修改现有架构，不自行引入依赖。
2. 优先复用已有组件、接口、工具函数和类型。
3. 禁止使用 any，新增代码符合项目规范。
4. UI 遵循 docs/AI-前端开发约束规范.md。
任务：填写目标功能、涉及文件、限制条件、已有结构和预期结果。
请先分析实现方案，不要直接输出代码。
```

### 代码审核

```text
请作为高级前端工程师审核以下代码。
检查架构、类型、性能、安全和可维护性问题。
依据项目规范列出问题、影响及修改建议，不要直接重写。
```

## 十六、最终原则

先理解，再设计，后编码；小步修改，避免无关重构；复用优先，新增谨慎。代码可运行不代表代码合格。

AI 负责提高开发速度；开发者负责架构、质量、安全及长期维护，并对生成代码进行人工审核。

## 附录：项目 UI 实施标准

以下标准与上述开发约束共同适用，用于保持本项目已有的视觉与交互一致性。

仅面向桌面大窗口设计和验收，不做中、小窗口或移动端适配。禁止自行添加响应式断点、移动导航抽屉、按窗口宽度重排布局或将多列表单改为单列；窗口缩小时保持桌面结构。

### 视觉与布局

- 采用紧凑运维控制台布局，以蓝色主操作、石墨色顶栏、中性灰背景和浅色面板建立视觉层级。
- 顶栏高 40px，背景使用 `--ui-header-bg`，文字使用 `--ui-header-text`，保留 autops 品牌；主导航展开宽 200px、收起宽 54px，菜单项高 38px。
- 导航选中项使用主色文字和左侧 3px 指示条；主导航与页面内的分组筛选区分开。
- 内容区占满剩余宽度，背景使用 `--ui-canvas`，内边距 20px；禁止通过居中窄容器制造左右大块留白。
- 页面按“面包屑、紧凑标题、工具栏、数据区”组织；列表页以表格为核心。
- 固定顶栏只预留一次高度。明确各区域的滚动容器，避免重复偏移、内容裁切和整页横向溢出。
- 模块间距 16px，控件间距 8px；输入控件直角，小按钮圆角 2px，表格顶部可用 5px 圆角。
- 普通面板依靠背景与细边框分层，浮层可使用轻微阴影。禁止无业务用途的欢迎横幅、巨型标题、装饰卡片、渐变、玻璃效果和大圆角。

### 颜色

#### 配色原则

- 配色由本项目独立制定。禁止复制、套用或以复刻为目标模仿已有软件的品牌色、主题色板及其组合关系；不得从其他产品截图、样式源码或组件库预设主题直接提取色板。
- 遵循通用颜色语义：蓝色表示主操作与信息，红色表示删除与错误，绿色表示成功，琥珀色表示警告，中性灰用于背景和次要操作。不得为追求独特而颠倒语义；借鉴设计原则不等于复制产品色板。
- 全部颜色集中为下表中的 CSS 自定义属性；页面和组件引用变量，不各自添加硬编码颜色。白色、灰色等通用颜色可以使用，禁止直接照搬其他产品的整体配色方案。
- 本规范定义浅色主题。不得自行增加另一套主题；调整颜色时同步更新变量、交互状态及对比度验证。

| 危险、错误 | `--ui-danger` / `#B13737`  | `--ui-danger-soft` / `#FAECEC`  |

- 主色用于主要操作、真实链接与导航选中，不大面积铺满内容区。导航选中采用主色文字、浅主色背景与左侧指示条。
- 同一操作区域只保留一个高强调主操作；新增、保存使用蓝色，编辑使用蓝色或中性文字按钮，刷新与取消使用中性按钮。不得将新增染红，也不得将删除染绿。
- 状态提示与标签采用对应浅底和深色前景，必须显示状态文字，可配图标；不用整行高饱和背景表达状态。测试状态统一采用下文规定的图标与 tooltip，状态文字通过 tooltip 和可访问名称提供。
- 默认删除操作使用危险色文字，hover 使用危险浅底；实心危险按钮使用危险色背景与白字。错误输入框边界使用危险色，不能仅修改帮助文字颜色。
- 中性按钮使用面板底色、正文色和控件边框，hover 使用次级区域底色。禁用状态使用专用变量，禁止降低整个组件 opacity 导致文字与边框不可辨识。
- 键盘焦点使用主色 2px 外轮廓，偏移 2px；不能只靠 hover 或微弱背景变化提示焦点。
- 深色顶栏上的焦点轮廓使用 `--ui-header-text`，确保与顶栏背景有足够对比。

#### Element Plus 映射与对比度

- `--el-color-primary` 及其 `dark-2` 分别映射主色、主色 hover；按钮按下态显式采用 `--ui-primary-active`。success、info、warning、danger/error 映射对应语义前景色。
- 背景、正文、辅助文字、placeholder、控件边框同步映射对应 Element Plus 变量；菜单、表格、弹窗及传送到 body 的浮层均应用同一主题，不残留组件库默认色板。
- 组件库需要的 `light-3/5/7/8/9` 按基础色与白色以 30%/50%/70%/80%/90% 的白色占比在 sRGB 通道混合后统一生成。交互与状态浅底优先使用明确指定的变量。
- 普通文字与背景对比度至少 4.5:1；控件边界及焦点标记与相邻背景至少 3:1。装饰性分隔线不承担控件辨识职责。
- 每次调整色板后重新核算实际组合，包括主按钮白字、顶栏文字、辅助文字、状态浅底、控件边界和焦点。透明叠加与派生色按实际背景检查。

### 字体

- 使用系统字体栈：`"Open Sans", "Helvetica Neue", Helvetica, Arial, "PingFang SC", "Microsoft YaHei", sans-serif`，不引入字体下载依赖。
- 正文 13px，行高约 1.43；辅助信息 12px，行高 18px。
- 页面标题 18px / 600，分区标题 14px / 600，弹窗标题 16px，菜单文字 12px。
- 长名称、地址和说明应可查看完整内容，不得因固定宽高丢失关键信息。

### 表格与工具栏

- 工具栏主要操作放左侧，搜索、筛选和刷新放右侧；同一工具栏控件高度一致。
- 表格文字 13px、行高 1.5，表头纵向内边距 8px、正文单元格纵向内边距 6px。
- 表头使用 `--ui-surface-muted`，正文使用 `--ui-surface`，横向分隔线使用 `--ui-border`；常规单元格不添加纵向网格。
- 单行目标高度约 36–40px，双行信息自然增高，不锁死行高。名称为主信息，地址等为辅助信息。
- 行 hover 使用 `--ui-row-hover`，选中态使用 `--ui-primary-soft`。操作列放右侧，宽表按需固定操作列并在表格容器内横向滚动。
- 名称只有在存在真实跳转入口时才显示链接样式。
- 分组筛选栏宽 220px；平面分组使用列表，不伪造层级树。
- 批量操作、在线状态和统计仅在业务及数据支持时展示，不为补齐界面而虚构功能。

### 列表分页

- 所有列表页必须提供分页功能，适用于已有列表页和新增列表页，不得因当前数据量较少而省略分页。
- 分页控件必须提供每页 10、20、50 条的数量选择，并支持切换页码；列表实际展示的数据量须与当前页码及每页数量一致。
- 切换每页数量或修改搜索、筛选条件时，将页码重置为第一页，并按更新后的条件加载或展示数据。
- 优先复用已有分页组件、接口和类型；分页总数与列表数据必须来自真实数据，不得虚构总数或使用备用数据掩盖请求失败。

### 测试状态展示

- 所有连接测试、模型测试及后续各类测试状态统一复用 `frontend/src/components/TestStatus.vue`，状态类型使用 `frontend/src/types/testStatus.ts`；禁止各页面重复绘制图标、维护颜色或自行改用状态标签、纯文字展示测试状态。
- 采用主机连接测试的 18px 圆形轮廓图标，不仅依赖颜色区分状态：`passed` 为绿色勾，`failed` 为红色叉，`pending` 为蓝色省略号，`warning` 为琥珀色感叹号，`untested` 和 `unavailable` 为灰色问号。颜色引用既有语义变量，禁止硬编码。
- 图标必须提供中文 tooltip 和相同含义的可访问名称，说明测试对象、当前状态及已知的使用限制；未测试、排队、测试中、已中断、待确认和状态待刷新须用提示文案明确区分。请求错误仍由统一反馈入口处理，tooltip 不重复展示请求错误详情或推断原因。
- 独立图标支持 Tab 聚焦及可见焦点，鼠标悬停和键盘聚焦均可查看提示；放在已有可聚焦按钮内时使用 `focusable=false`，通过 `tooltipVisible` 随外层按钮聚焦显示提示、失焦恢复自动触发，避免增加重复的 Tab 停靠点。
- 共用组件只负责图标、语义颜色、tooltip 和可访问性。业务组件负责请求、轮询、状态映射与提示内容；同类业务的映射和文案复用同一个展示函数，SSH 测试使用 `frontend/src/components/sshTestDisplay.ts`。
- 多项检测合并显示时，仅全部必需检测通过才能显示通过图标并开放依赖功能。任一必需检测失败显示未通过，尚未完成检测不得显示通过；进行中的测试优先显示测试中。AI 运维要求对话和工具调用两项检测全部通过，页面仅显示一个测试状态，不向普通用户展示协议术语。
- 测试历史、批量测试和详情中的状态指示同样复用共用组件；必要的业务详情、确认操作及测试失败说明仍由业务页面保留。

### 按钮与表单

- 常规按钮高 30px、字号 13px、内边距 8px 12px、圆角 2px。
- 主动作使用主色实心按钮，次要动作使用中性描边按钮，行内操作使用紧凑文字按钮，删除使用危险色。
- 输入、选择、数字输入等常规控件高 30px、字号 13px、圆角 0；多选控件允许随内容增高。
- 控件只显示单层边框，避免 wrapper 边框与 Element Plus 内嵌阴影叠加；聚焦使用主色边框，错误使用危险色边框。
- 表单按业务分区，字段间距 20px；短字段可排两列，不按窗口宽度改变列数。
- 标签与控件关联，必填标识使用 `--ui-danger`；placeholder 不能代替标签。帮助文字位于字段附近。
- 禁用状态清楚可辨；图标按钮提供可访问名称。

### 展开详情与折叠面板

#### 适用范围与语义

- 本节适用于点击后在当前页面显示或隐藏详情的控件（Disclosure），包括“相关报错详情”；多个相关内容分区使用折叠面板（Accordion）。这类控件执行展开操作，必须具有按钮语义，不能使用页面跳转链接冒充。
- 只折叠按需查阅的补充信息。错误等级、问题名称、影响主机、原因分析和处理建议等核心信息保持可见；不得为压缩页面隐藏用户完成当前任务必需的信息。避免折叠面板相互嵌套。

#### 可点击性与视觉状态

- 展开入口在鼠标未悬停、未聚焦时就必须能识别为交互控件。禁止仅显示与正文或普通标题相同的文字，禁止只依靠 hover、颜色变化或 tooltip 告知用户可以点击。
- 单项详情入口默认采用紧凑中性描边按钮外观：高 30px、字号 13px、水平内边距 12px、圆角 2px，背景使用 `--ui-surface`、文字使用 `--ui-text`、单层边框使用 `--ui-control-border`。沿用次要操作层级，不使用高强调实心主按钮。
- 分组折叠面板使用整行标题点击区域，最小高度 36px、水平内边距 12px，标题使用 13px / 600；默认背景使用 `--ui-surface-muted`，区域分隔线使用 `--ui-border`。标题、状态箭头和展开/收起文字均属于同一点击区域，不能只允许点击小箭头。
- 状态箭头统一放在标题文字左侧，与文字间距 8px，大小 14px；收起时朝右，展开时朝下。箭头在两种状态下始终可见，并与文字保持相邻，不得放在宽面板远端导致用户难以发现。装饰性箭头对辅助技术隐藏，状态由按钮语义提供。
- 文案须同时说明动作和内容。单项详情使用“展开相关报错详情”与“收起相关报错详情”；分组面板保留简短分区名称并显示“展开”或“收起”。不得只写“更多”“详情”或依赖箭头猜测操作。数量可选，必须来自真实数据且明确单位。
- hover 使用 `--ui-row-hover`，按下时使用 `--ui-surface-muted`；键盘焦点沿用主色 2px 外轮廓、偏移 2px，不得被容器裁切。展开状态通过箭头方向与文字共同表达，不能仅靠颜色区分。按钮和标题区域的文字、控件边界及焦点对比度沿用本规范要求。
- 展开内容紧随触发控件下方，与对应问题保持在同一视觉分组；触发控件保留原位，展开后仍可直接收起。隐藏内容及其内部控件不得保留在 Tab 顺序中。用户在内容内触发收起时，应将焦点返回对应展开入口。

#### 实现与可访问性

- 优先复用 Element Plus `ElCollapse` / `ElCollapseItem` 或 `ElButton` 及已有共用样式。定制折叠标题时复用组件的展开状态，不额外维护一套互相独立的状态；不得在已有按钮语义的标题内嵌套另一个按钮或链接。
- 控件可通过 Tab / Shift+Tab 聚焦，Enter 和 Space 均可切换展开状态，一次操作只切换一次。自定义控件优先使用原生 `button` 并设置 `type="button"`；沿用组件按钮语义时验证其实际输出和键盘行为，不因修改外观破坏原有语义。
- 按钮的 `aria-expanded` 必须与实际可见状态同步，收起为 `false`、展开为 `true`；项目要求用 `aria-controls` 关联详情容器的唯一 ID。同页多个问题、多个工作区页面的 ID 均不得冲突。可访问名称须说明展开的对象；需要补充问题名称时避免将整段分析纳入按钮名称。
- 展开动作保持当前页面上下文，不自动跳转页面或将焦点移入详情。无详情时不显示可操作的展开入口；异步加载的详情沿用现有 loading 与统一请求错误反馈，失败不得显示为正常空数据。

以上控件尺寸、配色、箭头位置及文案形式为项目统一约定；外部指南提供交互模式、内容组织和可访问性依据，不要求复制其品牌配色或组件外观。

### 弹窗与反馈

- 弹窗在视口内居中，标题 16px，页脚右侧按“取消、保存”排列。
- 简单表单宽约 440px，复杂表单宽约 720px，均不得超过视口；长内容可滚动，操作按钮始终可达。
- 区分加载中、无数据、搜索无结果、加载失败、字段错误和保存中。
- 保存中显示 loading 并阻止重复提交；请求失败终止当前操作并恢复加载或保存状态，不显示成正常空数据或成功。
- 危险操作确认说明具体对象与影响。视觉修改保留现有校验、凭据处理、冲突处理和确认语义。

#### 错误提示与状态管理

- 错误按来源区分为前端本地校验错误与请求错误，两类错误分别处理。必填、格式、文件大小等本地校验可在字段或表单附近显示具体原因；前端已知的操作前置条件可使用消息提醒。提示采用与错误或警告含义对应的图标和语义色。
- 后端接口错误、网络失败、请求超时、响应读取失败及 JSON 解析失败由请求层统一转换为明确的请求错误类型并抛出，不得返回默认值、备用数据或吞掉异常后继续成功流程。当前请求错误的统一展示文案为“系统异常”；不得展示、翻译或改写后端错误详情，也不得根据错误内容或 HTTP 状态码推断原因、提供建议操作。
- 通用错误文案集中维护，同一语义的文案只有一处定义，错误对象和展示入口按需复用；页面不得各自硬编码、拼接或改写通用错误文案。具体字段校验文案由对应表单维护，不要求所有错误使用相同文字。
- 请求错误统一通过共用反馈入口使用顶部居中的 `ElMessage` 提示，距顶部 16px，显示 3000ms 后自动关闭，不遮挡操作、不要求确认。首次加载、刷新、搜索及新增、编辑、删除等操作遵循相同规则；页面、分组栏、表格空态、单元格及表单内不得重复展示请求错误文案或持久错误条。
- 共用反馈入口统一维护消息的位置、样式、时长及重复合并规则，页面不各自配置。同类错误在提示可见期间合并为一条，不叠加消息或重复次数标记；关闭后再次发生错误可重新提示。
- 提示文案仅用于展示，业务状态使用明确的布尔值、枚举或其他状态标识独立记录；已有加载状态足以表达依赖数据未成功加载时可复用。禁止通过错误文案的赋值、相等比较或内容匹配判断业务状态；校验结果须用类型或状态标识区分本地校验与请求错误。
- 列表加载、详情读取、保存和删除的状态按操作分别管理。编辑、保存或删除请求失败不得标记为列表加载失败；操作成功后重新加载列表失败时，才更新对应列表的失败状态。再次加载成功后恢复正常数据或空态展示。
- 页面负责请求失败后的操作终止、loading 或保存状态恢复及表单内容保留；失败后不得关闭未保存成功的表单、提示成功或执行依赖成功结果的后续步骤。共用请求层不直接弹消息；有请求序号或失效判断的页面仅处理当前有效请求的错误，失效请求不得更新状态或弹出提示。
- 消息消失不代表请求成功。保留内部加载失败状态，失败时不渲染“暂无数据”等正常空态或新增引导；依赖数据未成功加载时阻止后续操作，不使用备用数据或把失败当作空列表成功处理。

### 桌面范围与可访问性

- 保持桌面侧栏、分组栏与表格的固定结构；侧栏仅由用户操作展开或收起，不随窗口宽度切换。
- 宽表格在自身容器横向滚动；桌面窗口内保证弹窗、下拉面板与操作按钮可达。中、小窗口不作为适配或验收目标。
- 保留可见的键盘焦点，支持 Tab 操作，弹窗保持合理的焦点进入与返回行为。
- 检查文字、按钮与背景的对比度；不可通过删除焦点样式或进一步缩小字号来压缩界面。

### 验收

- 页面布局、颜色、字号、控件尺寸与本规范一致，跨页面复用统一样式和组件。
- 逐项检查标题、字段、提示、tooltip、统计和详情的用户用途；删除无用或重复内容，确认必要状态、风险、业务证据及可访问名称仍完整，且未直接展示接口原始对象或内部调试信息。
- 所有列表页均具有分页控件及每页 10、20、50 条的数量选择；检查页码切换、每页数量切换及搜索、筛选后重置页码的行为，确认展示数据与分页状态一致。
- 检查加载、空数据、错误、保存中、长文本和长表单状态。
- 展开详情验收覆盖默认、hover、聚焦、展开、收起及无详情状态：默认入口可识别且箭头紧邻文字；点击整个控件、Enter 和 Space 均可切换；文案、箭头、`aria-expanded` 和内容可见性一致；`aria-controls` 正确关联唯一容器；收起后内部控件不可 Tab 聚焦，长内容不挤掉或裁切收起入口。
- 错误反馈验收覆盖同类错误并发发生时只显示一条消息、失效请求不提示、失败不显示正常空态、重试成功恢复展示、保存失败保留表单，以及本地校验与请求错误互不混用；检查通用错误文案集中维护、反馈配置通过共用入口复用且页面不依赖文案判断状态。

本文件为项目统一实施规范，配色独立制定，不采用已有软件的主题色板。

配色原则依据：[Atlassian 颜色角色与交互状态](https://atlassian.design/foundations/color)、[Carbon 主操作与危险按钮](https://carbondesignsystem.com/components/button/usage/)、[W3C WCAG 颜色不能作为唯一提示](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)。借鉴其语义、层级和可访问性原则，不采用其品牌色板。

即时反馈交互依据：[Element Plus Message](https://element-plus.org/en-US/component/message)。采用其顶部消息和 3 秒自动关闭方式，同类重复错误由项目共用反馈入口合并。

最小必要信息原则依据（检索与核对日期：2026-10-14）：[Nielsen 美观与极简设计](https://www.nngroup.com/articles/aesthetic-minimalist-design/)要求删除不支持用户任务的内容，并保留完成任务所需的全部元素；[Nielsen 渐进式披露](https://www.nngroup.com/articles/progressive-disclosure/)要求常用必要内容优先展示，次要内容按需呈现且入口清晰；[Nielsen 信息污染](https://www.nngroup.com/articles/information-pollution/)说明冗长文字和无价值细节会妨碍有效信息的提取。本项目据此制定第 9.1 节及对应审核要求，具体错误反馈仍遵循本项目既有约定。

展开详情与折叠面板依据（检索与核对日期：2026-10-14）：[W3C WAI-ARIA Disclosure 模式](https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/)规定按钮语义、展开状态与 Enter / Space 操作，介绍右向/下向箭头提示；[GOV.UK Details](https://design-system.service.gov.uk/components/details/)要求简短且描述内容的入口，不隐藏多数用户必需的信息，并指出入口可能被误认为跳转链接；[GOV.UK Accordion](https://design-system.service.gov.uk/components/accordion/)说明整段标题点击区域、显示/隐藏动作提示及避免嵌套；[Element Plus Collapse](https://element-plus.org/en-US/component/collapse.html)提供标题/图标插槽、`isActive` 状态与 `expand-icon-position` 配置，供既有组件定制使用。
