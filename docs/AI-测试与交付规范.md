# AI 测试与交付规范

## 一、证据与检查配置

实施者必须按第三节限定的验证方式执行，记录真实命令、环境、范围及结果；审核者核对证据和缺口，负责人批准工具、例外和发布条件。禁止把文件已写入、构建通过、技能存在或模型自评等同于业务正确、人工通过或生产可用。

本包没有目标项目代码、依赖或 CI，未预置任何项目检查已可执行的结论。必须从目标依赖清单、脚本、构建和测试配置确认真实命令，记录在 [项目配置](../项目配置.md)，禁止猜测 npm、pytest、Ruff、ESLint 或扫描命令。

后端运行启动测试、前端打包测试分别登记“已配置、未配置、不适用、已执行及结果”。其他检查可以记录既有配置，但禁止因已配置就自动执行；按第三节未执行的检查必须如实注明原因和覆盖限制。Git 状态、差异和空白检查可用于核对文件范围，不能替代业务验证。

## 二、测试政策与设计

本包沿用所有测试文件及验证脚本仅本地、不暂存、不提交、不通过忽略例外强制添加的基线；它不授权删除或弱化测试。已有项目不同政策先按治理流程决定，禁止导入自动取消跟踪现有测试。采用本地基线后，克隆仓库不保证测试存在，检查前核实路径与受控来源，禁止把空收集或缺失当成功。

仅本地政策是本包的明确选择，不是通用行业要求。目标项目采用时记录理由、维护责任、受控版本及在干净环境取得和运行验证的方式；不能提供时明确可复现性缺口，不声称仓库本身具备持续回归能力。

仅在用户明确另行要求专项测试时，按其授权范围补充或执行测试；禁止因普通前后端改动或缺陷修复自动增加回归测试。专项测试优先验证可观察行为、业务不变量和稳定契约，禁止只复制实现或为低风险可逆改动堆叠无价值测试；无法自动化时说明原因、人工步骤和结果。

获准的专项测试覆盖其范围内的正常、失败和边界，可独立运行、使用隔离虚构数据并清理自身数据；控制时间、随机、网络和外部依赖，禁止测试顺序或生产资源成为隐含依赖。

## 三、按变更类型验证

后端改动的执行验证仅进行运行启动测试，前端改动的执行验证仅进行打包测试；同一任务同时涉及两端时，分别执行对应测试。适用范围包括各端的源码、样式、配置及依赖改动。禁止自动追加独立的格式、代码规范、类型、单元、组件、接口、契约、端到端、浏览器、迁移、并发、性能或安全扫描等检查，也禁止用人工业务操作替代追加测试。本节统一约束其他规范、专项和模板中的测试执行要求；其中正常、异常、边界、权限、兼容及界面要求仍作为源码、配置与差异审核依据，禁止据此声称已完成运行验证。用户明确另行要求专项测试或独立授权合并、发布任务时，按其明确范围执行。

只允许验证本次修改内容及有明确依据的直接影响，禁止扩大到无关模块、页面、流程、设备或环境。必须从实际配置确认对应应用的启动或打包命令；应用启动或打包无法按文件缩小时，可以执行该受影响应用的完整命令，必须说明覆盖范围，禁止扩大到无关应用或整个仓库。既有命令内置的类型检查等必要步骤随命令执行，禁止为满足“仅启动/打包”拆改脚本、关闭检查或放宽既有门禁；命令额外串联无关测试时，必须说明冲突及未执行项，禁止擅自绕过。

| 变更 | 允许执行的验证与通过依据 |
| --- | --- |
| 纯文档、规范、独立文案文件 | 检查实际内容、来源、命令与路径、引用、Markdown 及最终差异；不执行应用测试。应用源码中的文案修改按所属端执行 |
| 后端改动 | 仅运行启动测试：在本地或已授权的隔离环境使用实际入口启动，依据项目既有启动完成信号及必要的进程存活或监听状态确认启动，无启动异常；仅进程被创建不能判为通过。禁止追加业务接口请求或流程测试 |
| 前端改动 | 仅打包测试：执行受影响应用实际配置的打包命令，以退出码为零且生成预期构建产物为通过依据；开发服务器启动不能替代打包。禁止追加浏览器、页面或交互测试 |
| 前后端同时改动 | 分别执行后端运行启动测试和前端打包测试，并分别记录结果；一端通过不能替代另一端的证据 |

启动测试必须记录启动完成的判断依据和观察结果；结束或失败后必须停止本次创建的进程并释放资源，禁止误停已有服务。启动会执行迁移、生产写入、真实费用或其他需授权副作用时，必须先按既有授权边界处理，禁止借启动测试自动授权。打包必须核对产物位置，禁止将构建产物提交 Git。命令、依赖或环境缺失以及测试失败必须如实报告，禁止自行换成其他测试、伪造结果或屏蔽失败。

启动通过仅证明所测环境下能够启动，打包通过仅证明所测配置下能够生成产物；交付必须明确业务行为、接口正确性、安全、迁移及界面交互等未被这两类测试覆盖。源码与差异审核、既有安全要求、人工审核和生产授权继续执行，禁止因缩减测试而删除测试文件、修改 CI 或降低门禁。另行获准的界面测试沿用已批准视口和设备范围；性能阈值由需求或测量给出，不凭空设定。

## 四、失败与质量门禁

失败读取完整错误，区分本次、既有与环境问题；按证据定位，在授权范围修复后仅重跑对应检查。新改动、失败或未消除风险不构成扩大验证范围的许可；范围外问题只报告，不追加验证或修复。仅当范围内有新改动使原结果失效、检查失败待确认修复或验收项尚无证据时，允许重复对应验证；适用验收和必需检查通过后立即结束。禁止关闭检查、删除测试、放宽断言、吞异常、降低阈值或用 `|| true` 制造通过。

必需检查缺失、跳过、无法执行与失败分别说明。CI 中不能静默跳过必需脚本；缺失时明确失败或进入经批准的初始化/例外状态，记录原因、影响、替代措施、责任、恢复条件及到期。测试只本地时，CI 的测试来源与复现机制必须另行明确，不能伪称干净克隆即可运行。

未配置工具不是通过证据；无法关键验证且继续会有实质风险时，暂停依赖步骤并报告阻塞。禁止把与本任务无关的既有故障混入无关重构。

## 五、审核与完成定义

审核目标/验收、范围、复用、分层、类型、状态、错误、资源、契约消费者、权限/秘密、兼容/迁移/恢复和文档引用，核对最终差异无意外文件、数据或产物；具体按三份核心规范及适用专项执行。

规则文件、技能、MCP/客户端权限、依赖锁文件、安装钩子和 CI 配置等改动单独核查实际行为、授权和外部访问。独立 AI 审核应核对差异及需求证据，报告影响正确性或验收的问题，不以实施者摘要替代检查，也不凭风格偏好扩大范围；人工审核要求仍然有效。

“完成”要求本次适用验收和必需验证有证据；有明确未完成项为“部分完成”，缺少继续条件为“阻塞”，关键验证未执行或不确定为“未验证”。完成不等于提交、人工批准或上线；项目本就未配置且本次不要求建设的工具列为现状，禁止伪称通过或无限扩大任务。

交付包含变更内容、主要文件、实际命令/人工步骤及结果、未执行与原因、覆盖限制、兼容风险和后续事项。AI 自评不能代替要求的人工审核。

## 六、Git 与协作

修改前后检查状态、分支及差异，保留用户工作；只暂存任务相关文件。提交、推送、创建合并请求、改平台保护及发布需要对应授权。获准提交时检查 `git status`、`git diff`、`git log --oneline -10`，沿用仓库风格并核查跟踪清单与暂存区，禁止秘密、测试（采用本包基线时）、运行数据、环境及构建产物进入提交。

禁止未经授权硬重置、强推、重写共享历史、删除远程分支或清理他人工作，也禁止为提交格式改写无关历史。每次提交聚焦一个目的；合并请求使用 [统一模板](templates/合并请求模板.md)。平台、分支策略与保护规则需真实核实，不从模板推定 GitHub 或 CI 已建立。

## 七、环境、发布与恢复

准备运行/发布前明确实际环境及隔离、配置名称/默认/敏感性、依赖版本与可重复构建、源码和产物对应、部署前检查、迁移顺序、健康与就绪覆盖、脱敏日志/保留期、指标告警、故障处置及负责人。不适用说明原因，未配置或未验证如实记录。

身份、worker/实例和任务协调来自实际实现与部署，禁止预设进程数或未经验证就声称具备多实例安全。健康接口响应不等于数据库、外部服务和任务全部就绪。

备份范围必须覆盖实际持久数据、凭据密钥及恢复所需配置；在线或停服方式按目标一致性机制决定，不能只备数据库就声称可恢复。负责人确定频率、保留期、位置、权限、加密和演练周期，重要迁移前确认备份与恢复。

含秘密、个人数据或敏感业务信息的备份必须加密、按最小权限访问并记录访问；策略未定不能视为允许明文保存。恢复在隔离环境验证并记录结果与耗时，备份存在或任务成功不等于恢复成功。未经授权禁止删备份、覆盖恢复点或缩短保留。

高风险发布明确触发回滚条件、应用/数据兼容、前向修复、恢复和负责人；不可逆影响提前说明并按授权执行。生产、网络/密钥、真实费用及外部副作用按根工作约定处理，已授权准备和可逆修复继续执行，不以清单增加重复审批。
