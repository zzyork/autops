# AI 测试与交付规范

## 一、证据与检查配置

实施者按风险选择验证，记录真实命令、环境、范围及结果；审核者核对证据和缺口，负责人批准工具、例外和发布条件。禁止把文件已写入、构建通过、技能存在或模型自评等同于业务正确、人工通过或生产可用。

本包没有目标项目代码、依赖或 CI，未预置任何项目检查已可执行的结论。必须从目标依赖清单、脚本、构建和测试配置确认真实命令，记录在 [项目配置](../项目配置.md)，禁止猜测 npm、pytest、Ruff、ESLint 或扫描命令。

格式/代码规范、类型、单元/组件、接口/契约、浏览器、安全、迁移/并发、性能、构建和启动等检查分别登记“已配置、未配置、不适用、已执行及结果”。Git 状态、差异和空白检查可用于核对文件范围，不能替代业务验证。

## 二、测试政策与设计

本包沿用所有测试文件及验证脚本仅本地、不暂存、不提交、不通过忽略例外强制添加的基线；它不授权删除或弱化测试。已有项目不同政策先按治理流程决定，禁止导入自动取消跟踪现有测试。采用本地基线后，克隆仓库不保证测试存在，检查前核实路径与受控来源，禁止把空收集或缺失当成功。

仅本地政策是本包的明确选择，不是通用行业要求。目标项目采用时记录理由、维护责任、受控版本及在干净环境取得和运行验证的方式；不能提供时明确可复现性缺口，不声称仓库本身具备持续回归能力。

测试优先验证可观察行为、业务不变量和稳定契约，禁止只复制实现或为低风险可逆改动堆叠无价值测试。可自动复现且有回归风险的缺陷补充本地回归；无法自动化时说明原因、人工步骤和结果。

验证覆盖正常、失败和边界，测试可独立运行、使用隔离虚构数据并清理自身数据；控制时间、随机、网络和外部依赖，禁止测试顺序或生产资源成为隐含依赖。

## 三、按变更类型验证

| 变更 | 必须核查的范围 |
| --- | --- |
| 纯文档、规范、文案 | 实际内容、来源、命令与路径、引用、Markdown 及最终差异；无需无关应用测试 |
| 前端代码 | 实际已配置类型检查与构建，受影响状态和业务验证；工具缺失如实报告 |
| 界面或用户流程 | 项目配置批准的设备/视口、加载/空数据/失败/保存/长内容、键盘、焦点、危险及取消路径；浏览器不可用明确未验证 |
| 业务或缺陷 | 正常、异常、边界与回归，用本地测试或可复现人工步骤验证 |
| API、流与下载 | 输入输出、状态码、权限、字段过滤、真实事件/内容、错误、取消及消费方兼容 |
| 数据、事务及迁移 | 旧数据、顺序、回滚、重复执行、并发不变量；不可逆操作先授权并验证恢复 |
| 权限、安全、文件或秘密 | 允许与拒绝、越权、异常输入、超限、脱敏和泄露风险 |
| 依赖、启动、部署 | 版本、配置、构建/启动、健康、生命周期、访问和恢复 |
| 跨模块或重大重构 | 扩大到受影响的公共接口和关键流程，禁止用无关检查替代覆盖 |

界面验收按项目配置及已启用 UI 模板中批准的视口和设备范围执行，不预设 1440px 或仅桌面；禁止通用测试自动扩大或删减已批准设备。性能阈值由需求或测量给出，不凭空设定。

## 四、失败与质量门禁

失败读取完整错误，区分本次、既有与环境问题；按证据定位，在授权范围修复后重跑对应检查。只有新改动、失败或未消除风险才扩大/重复验证。禁止关闭检查、删除测试、放宽断言、吞异常、降低阈值或用 `|| true` 制造通过。

必需检查缺失、跳过、无法执行与失败分别说明。CI 中不能静默跳过必需脚本；缺失时明确失败或进入经批准的初始化/例外状态，记录原因、影响、替代措施、责任、恢复条件及到期。测试只本地时，CI 的测试来源与复现机制必须另行明确，不能伪称干净克隆即可运行。

未配置工具不是通过证据；无法关键验证且继续会有实质风险时，暂停依赖步骤并报告阻塞。禁止把与本任务无关的既有故障混入无关重构。

## 五、审核与完成定义

审核目标/验收、范围、复用、分层、类型、状态、错误、资源、契约消费者、权限/秘密、兼容/迁移/恢复和文档引用，核对最终差异无意外文件、数据或产物；具体按三份核心规范及适用专项执行。

规则文件、技能、MCP/客户端权限、依赖锁文件、安装钩子和 CI 配置等改动单独核查实际行为、授权和外部访问。独立 AI 审核应核对差异及需求证据，报告影响正确性或验收的问题，不以实施者摘要替代检查，也不凭风格偏好扩大范围；人工审核要求仍然有效。

“完成”要求本次适用验收和必需验证有证据；有明确未完成项为“部分完成”，缺少继续条件为“阻塞”，关键验证未执行或不确定为“未验证”。完成不等于提交、人工批准或上线；项目本就未配置且本次不要求建设的工具列为现状，禁止伪称通过或无限扩大任务。

交付包含变更内容、主要文件、实际命令/人工步骤及结果、未执行与原因、覆盖限制、兼容风险和后续事项。AI 自评不能代替要求的人工审核。

## 六、Git 与协作

修改前后检查状态、分支及差异，保留用户工作；只暂存任务相关文件。提交、推送、创建合并请求、改平台保护及发布需要对应授权。获准提交时检查 `git status`、`git diff`、`git log --oneline -10`，沿用仓库风格并核查跟踪清单与暂存区，禁止秘密、测试（采用本包基线时）、运行数据、环境及构建产物进入提交。

禁止未经授权硬重置、强推、重写共享历史、删除远程分支或清理他人工作，也禁止为提交格式改写无关历史。每次提交聚焦一个目的；合并请求使用 [统一模板](templates/合并请求模板.md)。平台、分支策略与保护规则需真实核实，不从模板推定 GitHub 或 CI 已建立。

## 七、环境、发布与恢复

准备运行/发布前明确实际环境及隔离、配置名称/默认/敏感性、依赖版本与可重复构建、源码和产物对应、部署前检查、迁移顺序、健康与就绪覆盖、脱敏日志/保留期、指标告警、故障处置及负责人。不适用说明原因，未配置或未验证如实记录。

身份、worker/实例和任务协调来自实际实现与部署，禁止预设进程数或未经验证就声称具备多实例安全。健康接口响应不等于数据库、外部服务和任务全部就绪。

备份范围必须覆盖实际持久数据、凭据密钥及恢复所需配置；在线或停服方式按目标一致性机制决定，不能只备数据库就声称可恢复。负责人确定频率、保留期、位置、权限、加密和演练周期，重要迁移前确认备份与恢复。

含秘密、个人数据或敏感业务信息的备份必须加密、按最小权限访问并记录访问；策略未定不能视为允许明文保存。恢复在隔离环境验证并记录结果与耗时，备份存在或任务成功不等于恢复成功。未经授权禁止删备份、覆盖恢复点或缩短保留。

高风险发布明确触发回滚条件、应用/数据兼容、前向修复、恢复和负责人；不可逆影响提前说明并按授权执行。生产、网络/密钥、真实费用及外部副作用按根工作约定处理，已授权准备和可逆修复继续执行，不以清单增加重复审批。
