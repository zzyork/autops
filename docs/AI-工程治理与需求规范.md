## 二、规则用语、优先级与变更

新增规范使用以下四种用语，写明适用对象、触发条件、行为和验证方式：

| 用语 | 含义与执行方式 |
| --- | --- |
| 必须 | 条款适用时强制执行，禁止自行跳过或降低要求 |
| 禁止 | 条款适用时禁止执行，仅适用条款明示的授权例外 |
| 应当 | 默认遵循；偏离前记录原因、影响、风险及替代措施，由项目负责人批准 |
| 可以 | 可选做法，不构成必需门禁 |

技术标识符、文件名、命令、产品和协议名称保持原样；解释、提示和交付优先使用中文。禁止仅用“优化”“稳定”“适当”“全面检查”等不可验证表述定义验收条件；阈值必须有需求、配置或测量依据。

既有规范中的“不得”“不允许”按明确的禁止要求执行，“建议”保留其推荐强度。本次合并不通过替换措辞改变原条款强度，也不要求为语言统一重写无关文档。

客户端系统指令与权限边界优先；在其允许范围内，执行用户当前明确要求、项目工作约定及开发规范、项目适配技能、外部参考。已批准的需求、数据语义和接口契约是实施边界，禁止默默改变。稳定既有实现用于理解上下文，不能作为忽略规范的理由。

遇到会影响架构、数据语义、兼容性、安全或主要流程的实质冲突，必须列出具体条款、影响和可行处理方式，暂停受影响部分并请求用户决策；独立且已授权的部分可以继续。已在接入指南或合并说明中明确处理的通用模板差异，按记录执行，不重复增加审批。

规范文件只有在用户明确要求时才能修改。变更时必须说明目的、影响及验证方式，并同步核查相关入口、模板、索引与检查配置；禁止为了使实现通过而削弱规则。

允许例外的条款必须记录规则编号或原文、原因、范围、风险、补偿措施、批准人及失效日期或复审条件。禁止把临时实现自动升级为永久例外，也禁止用项目例外绕过客户端权限与适用的强制安全要求。

## 四、需求与验收

实施前必须明确目标、范围、约束和完成条件；可以从仓库补齐技术背景。小任务在任务说明中记录即可，禁止为了填写模板要求用户重复提供可直接核实的信息。

中大型需求必须包含：

1. 背景、用户场景、目标、包含范围及明确排除项。
2. 正常流程、输入输出、校验、状态转换和数据所有权。
3. 权限与数据可见范围；当前不存在的角色或认证能力必须明确为拟新增内容。
4. 无数据、无效输入、资源缺失、冲突、取消、超时、依赖失败和边界场景中适用的行为。
5. 已确认的性能、安全、可访问性、兼容性要求，以及依赖、风险和待决策项。
6. 验收条件与验证方式。每条写清前提、触发操作和可观察结果；接口、数据结构变更分别补充契约及迁移说明。

例如：“给定当前页删除最后一条记录成功，重新加载后回到有效页码，数据与总数一致”；“给定保存请求失败，结束保存状态并保留表单，按统一入口提示‘系统异常’，禁止进入成功流程”。错误行为仍遵循前端规范。

影响很小且可逆的歧义，可以说明假设后继续。会改变架构、权限、安全、数据语义、兼容性、主要用户流程或导致不可逆影响的歧义，必须先澄清受影响部分。

新要求到来时必须更新任务范围和验收条件，并检查已有授权是否覆盖新增工作。只有出现新的决策或超出授权的实质影响时才请求确认；禁止无记录扩大任务后声称原验收已完成。

## 五、架构、依赖与兼容性决策

设计前必须阅读相关实现、调用方和配置，查找复用点，并说明目标、文件、影响、风险、必要复杂度及验证方式。拆分、合并和抽象采用奥卡姆剃刀规范；禁止仅凭调用次数决定边界，独立职责或隔离变化也可以构成边界依据。

新增、替换或升级依赖必须说明现有能力无法满足的需求、候选方案的维护状态、许可证、兼容性、安全情况、资源开销和维护责任。项目没有使用的 Axios、Pinia、VueUse、SQLModel、Asyncer、uv、迁移工具或扫描工具，禁止因为模板提及就自行引入。

更换框架、数据库、认证或部署方式，引入影响架构或安全的重要依赖，改变模块边界、数据所有权、API 版本策略，或存在长期成本取舍时，必须记录架构决策并按工作约定取得确认。使用 [架构决策记录模板](templates/架构决策记录模板.md) 说明背景、候选方案、理由、后果、验证和恢复方式。

公开接口、共享组件、导出类型、数据库字段和配置均是兼容性边界。删改前必须搜索消费者，明确迁移顺序、旧数据、并发写入和恢复影响。禁止以清空数据库、删除迁移历史、降低类型检查或移除测试来掩盖问题。

## 六、智能体实施流程与风险

1. **理解**：阅读适用规范、索引、源码、调用方和检查配置，核对 Git 状态与现有差异，保留用户工作。
2. **计划**：明确最小完整方案、文件、行为、契约、步骤、风险和验收。多步骤任务维护简短计划；较大任务使用 `docs/plans/`，小改动直接在任务说明中记录。
3. **实施**：按已授权范围小步修改。普通已授权开发不因跨文件或模板要求再审批；架构调整、大规模重构、数据迁移、新增兜底及超出授权的高风险行为按项目规则确认。
4. **验证**：执行 [测试与交付规范](AI-测试与交付规范.md) 中适用的检查，先定位失败根因，再修复有证据支持且属于任务范围的问题。
5. **审核与交付**：检查最终差异、契约、安全和文档，逐项说明实际结果及未验证项；人工审核、提交、推送与发布分别遵循授权。

| 风险 | 判断依据 | 处理方式 |
| --- | --- | --- |
| 低 | 纯文档、文案或无行为影响的可逆局部改动 | 明确范围后实施并检查内容与差异 |
| 中 | 普通业务逻辑、页面交互、兼容接口增补 | 记录验收与计划，验证失败路径及调用方 |
| 高 | 架构、安全边界、数据迁移、公开接口不兼容、用户数据或生产环境 | 说明影响、备份/恢复和验证，按既有授权判断是否需要确认 |

检查失败时禁止盲目反复试改。必须读取完整错误，区分本次问题、既有问题和环境问题；没有新证据时补充定位证据，缺少关键决策或权限时报告阻塞。禁止通过关闭检查获得通过，也不以固定尝试次数替代根因判断。

## 七、文档、索引与方案生命周期

同一主题必须明确一个权威来源；其他文档通过链接引用。具体界面标准只维护在前端规范，错误与响应边界只按对应契约维护，模板不重复定义规则。

| 变更类型 | 同步核查内容 |
| --- | --- |
| 功能与交互 | 需求、使用流程、验收场景及适用的 README 内容 |
| API、SSE 或下载 | 服务端模型、前端类型与消费逻辑、契约及验证记录 |
| 数据与迁移 | 迁移实现、顺序、数据影响、恢复说明 |
| 目录、文件职责或模块边界 | `FILE_INDEX.md`、架构说明及文档引用 |
| 依赖、配置或部署 | 依赖清单/锁文件、决策、环境变量示例及运行说明 |
| 安全机制或开发规范 | 对应规范、入口、模板及适用的检查配置 |

命令必须能追溯到真实配置；未执行的命令只能标注为“配置已核实，未执行”。未确定项明确记录状态、责任及需要的决策，禁止填写虚构联系人、通过记录或生产能力。

README 的模块顺序和全文 1000 字限制仍严格执行 `AGENTS.md`。详细工程规则通过贡献指南链接，不把整套规范复制进 README。

`FILE_INDEX.md` 用于定位，不代替阅读源码；文件职责或目录结构变化时同步更新，禁止添加方案文件条目。`docs/plans/` 中对应方案执行完成后必须删除；尚未实施的方案保留。需要长期保留的最终行为、契约或架构决定在删除方案前归入对应权威文档。

## 八、工程基线核查

规范接入或后续扩展时，维护者必须核查下列事项并区分已配置、未配置和不适用，禁止把清单当作已完成证明：

- 产品范围、验收条件、实际技术栈、入口、模块与契约。
- 单 worker、数据存储、身份与访问边界，以及桌面界面范围。
- 本地真实检查命令、测试文件政策、缺失检查及补齐条件。
- 人工审核、生产访问、发布、外部副作用和数据恢复的授权要求。
- CI、依赖/秘密扫描、分支保护、部署环境、监控和恢复演练的实际配置及负责人决策。
- 客户端是否实际发现并读取项目技能；文件存在不代表加载成功或规则已强制执行。

本次接入只整理规范。未配置能力及后续决策见 [规范合并说明](AI-规范合并说明.md)，禁止仅凭文档建立声称已满足上线条件。
