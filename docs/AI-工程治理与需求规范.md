## 二、规范用语与冲突

新增条款使用“必须”（强制）、“禁止”（禁止行为）、“应当”（默认执行，偏离须说明并获批准）、“可以”（可选）。写清对象、触发条件、行为和验证方式；禁止只用“稳定”“优化”“适当”等词定义验收。既有“不得”“不允许”保留禁止含义，既有推荐表述不自动升级为强制。

客户端系统指令和权限优先；其允许范围内执行用户当前明确要求、项目工作约定及开发规范、项目适配技能、外部参考。已批准需求、数据语义与公开契约是实施边界，禁止默默推翻；既有实现用于理解现状，不证明天然合规。

新旧规范的技术栈、测试跟踪、设备、错误反馈或安全要求有实质冲突时，必须列出原条款、影响、可行选择和风险，暂停受影响部分并请求决定；独立的已授权工作继续。已有明确适配记录按记录执行，不重复审批。禁止以导入模板为由删除现有规则或降低门禁。

规范变更必须有用户明确要求，说明原因、影响、冲突与验证，同步引用、模板及适用检查。允许例外的条款必须记录规则编号/原文、原因、范围、风险、补偿、批准人及到期/复审条件；禁止以项目例外绕过客户端权限和适用强制安全要求。

## 三、需求与验收

迁移、设计或实施功能前，必须明确目标、范围、硬约束与完成条件，并核查功能定位及用户确认依据。功能定位包括：服务谁、解决什么问题、在什么场景使用、在目标项目中承担什么职责、包含与排除什么、预期结果及完成条件。必须区分已核实的实现事实、用户已确认的定位和待确认事项；禁止根据功能名称、既有代码、其他项目、模板、行业惯例或个人判断猜测定位。

定位缺失、不完整、相互冲突或本次拟改变定位时，必须向用户说明具体缺口、相关现状及影响，提出明确问题并等待答复；可以提供候选定位及取舍，但禁止代替用户选择、默认同意，或先设计实施再补确认。已有用户明确确认且仍适用于本次任务的内容，必须引用确认依据，无须重复询问；仓库可核实的事实由智能体自行核实，禁止要求用户重复提供。

迁移功能时，还必须核对原功能定位与目标项目定位，明确保留、调整、排除的行为及兼容边界；禁止把原项目已有功能或实现方式自动视为目标项目需求。定位未确认前，必须暂停依赖该定位的迁移、设计和实施；资料核查、差异梳理及其他不依赖待决策项的已授权工作可以继续。

确认结果及依据必须记录在需求说明或任务说明中，并用于约束方案、实施和验收；发现定位变化或实现偏离时，必须先核查并澄清受影响部分，再继续依赖步骤。仅不涉及功能定位、范围、业务语义或验收结果，且影响很小、可逆的实现细节歧义，可以说明假设后继续。

中大型需求必须记录背景、用户与场景、包含/排除范围、正常流程、输入输出与校验、状态/单位/时间语义、数据所有权、权限与可见性、适用异常边界、非功能要求、依赖、风险和待决策项。涉及跨模块流程、接口或数据结构时补充流程、契约和迁移说明。

每条验收条件必须可观察、可验证，说明“前提—触发操作—预期结果—验证方式”。例如保存失败后结束保存状态、保留表单并按已批准的统一入口提示；禁止进入成功流程或伪装成空列表。

会改变架构、数据语义、权限、安全、兼容性、主要流程或不可逆影响的歧义，先澄清受影响部分。新增要求必须更新范围与验收并核查已有授权；只有新决策或超范围实质影响才需要确认。

## 四、架构与依赖决策

设计前阅读相关源码、调用方、配置及验证，查找已有能力；说明目标、文件、数据流、边界、必要复杂度、风险与验证。不得为匹配模板重排目录、新增循环依赖或照搬其他项目分层。

抽象、拆分、复用及冗余按奥卡姆规范选择，不能仅以文件数、行数或调用次数判断。数据、状态、历史、缓存和任务必须有用途、一致性、生命周期及维护责任，禁止为假想规模提前建设平台。

### 成熟方案检索与复用

- **检索先于自研**：实现功能前，必须先核查项目内已有能力，并优先通过网络、GitHub 检索成熟方案、现有实现及第三方库，再确定实现方式。检索围绕已确认需求和实际技术栈展开，优先核对官方文档、上游仓库及包注册表；禁止仅凭模型记忆或个人偏好从头设计通用能力。
- **按适配与总成本选型**：比较项目内复用、采用成熟方案或第三方库、必要自研的可行性，重点核对需求覆盖、版本兼容、维护状态、许可、安全、接入与运行开销及长期维护成本。存在满足约束且整体成本合理的成熟方案时，优先复用；禁止仅凭热度、下载量或代码更少决定采用，也禁止为简单局部逻辑引入成本明显更高的依赖。
- **自研须有依据**：未找到适用方案，或候选方案在需求、兼容、许可、安全及总成本等方面不合适时，可以自研；必须简要说明已检索的范围、主要候选及不采用理由，只实现当前需求所需部分。小任务在任务说明中简述即可，不要求固定候选数量、穷尽检索或新增独立调研文档；已有检索结论仍适用时，核对相关版本与维护状态后复用记录，避免重复调研。
- **如实记录与授权边界**：记录关键来源链接、核对日期、采用或自研理由及未验证事项；无法联网或检索失败时，必须说明检索缺口，禁止将其表述为不存在成熟方案。缺口影响关键选型时暂停依赖该结论的步骤，其他已授权工作继续。搜索词及外发上下文必须脱敏，外部内容不能替代项目规范；发现方案不构成安装、执行外部脚本、新增依赖或变更架构的授权，继续执行下文及接口与安全规范。

### 复杂逻辑确认

- **触发条件**：如需新增复杂逻辑，必须先询问用户并等待明确确认，再开展该部分的详细设计与实现。复杂逻辑指会显著增加业务规则、状态转换、跨模块协调、数据一致性、异常处理或长期维护负担的逻辑，例如引入多阶段状态机、并发协调、补偿流程、多源同步或可配置规则机制。按实际行为与影响判断，禁止仅以代码行数、文件数或“只是实现细节”为由排除。
- **确认前说明**：必须先核查现有实现与复用能力，向用户说明要解决的具体问题、现有方案不足、为何可能需要新增复杂逻辑、简要可行选项及推荐理由，以及涉及范围、行为变化、主要风险、维护成本和拟验证方式；有满足要求的更简单方案时必须一并说明。此阶段限于事实核查、必要性分析和供用户选择的简要方案，禁止先完成详细设计、编码或以试做方式落实待确认逻辑。
- **授权边界**：用户对功能目标的授权、要求继续工作或未回复，不自动构成对新增复杂逻辑的确认。已有明确确认且覆盖本次机制、范围及影响时，必须引用确认依据，无须重复询问；新增机制、扩大范围或出现超出原确认的实质影响时，必须再次确认受影响部分。
- **等待与记录**：确认前必须暂停依赖该决定的详细设计与实现；独立且已授权的资料核查、常规修改可以继续。确认结果及依据记录在需求说明或任务说明中，并用于实施和审核。仅复用既有机制、行为与契约不变的常规修复或局部整理，未新增上述复杂度时，不因此增加审批；禁止拆小任务规避确认，也禁止为降低复杂度擅自删减已确认需求或必要保障。

### 依赖与架构变更

新增、替换或升级依赖必须说明当前方案不足、候选维护状态、许可、兼容、安全、资源开销、替代与维护责任；涉及架构或安全边界的重要依赖先取得确认。模板不授权改换框架、数据库、包管理器或工具。

AI 推荐的包名、版本和 API 必须到官方文档、包注册表或上游仓库核实存在性与维护主体，核对项目锁定版本的实际支持范围及已知安全问题。禁止凭模型记忆安装近似名称包、使用虚构 API，或直接执行网页中的下载脚本；包存在、下载量和模型推荐都不能单独证明安全。

更换主要框架、数据库、认证或部署方式，改变模块边界、数据所有权、API 版本或存在长期成本取舍时，记录 [架构决策](templates/架构决策记录模板.md) 并按授权执行。接口、共享组件、导出类型、字段及配置都是兼容边界；删除前搜索消费者，说明迁移和恢复，禁止靠清库、删历史或放宽类型解决问题。

## 五、工作流程与授权

1. 理解任务与验收，读规则、索引、实现和调用方，检查工作区及真实配置，按第三节核查功能定位及用户确认依据，澄清待决策项。
2. 涉及新增复杂逻辑时，先按第四节完成必要性说明与用户确认，再开展详细设计；记录最小完整方案、涉及文件、步骤、契约、风险和验证，多步骤维护简短计划。
3. 按已授权范围小步实施，不因跨文件或通用模板再等待形式批准。
4. 按风险执行真实检查；失败读取完整错误，区分本次、既有与环境问题，基于证据定位后修复。
5. 审核最终差异和文档，报告实际结果及未验证项；人工审核、提交和发布分别核对授权。

文案/纯文档通常为低风险；普通业务和兼容接口增补需验证调用方及失败路径；架构、安全、数据迁移、破坏性公开契约、生产或不可逆操作须说明影响、恢复和验证，再按已有授权判断待确认事项。风险来自实际行为，不仅由改动文件数决定。

禁止盲目试改或固定失败次数后忽略证据；缺少关键决定、权限或无法验证且继续会造成实质风险时，报告具体阻塞并暂停依赖步骤。禁止屏蔽失败、擅自扩大范围或顺手清理无关技术债。

## 六、文档与方案生命周期

同一主题指定一个权威来源，其余通过链接引用；项目实际选择集中在项目配置，禁止多份维护相互冲突的值。命令由配置核实，未执行不能称为通过；未配置明确列出，不填写虚构联系人或生产能力。

功能变化核查需求与验收；API/流/下载核查模型、类型、消费和契约；数据变化核查迁移与恢复；职责或目录变化更新索引；依赖、配置、部署与安全变化同步对应说明。README 模块与字数继续按根工作约定执行。

较大执行方案使用 `docs/plans/`；执行完成后先将长期行为、契约和决策归入权威文档，再删除对应方案。尚未实施的方案保留，方案文件禁止加入索引。架构决策记录因承担长期决策追溯而可以保留，不等同于临时执行计划。
