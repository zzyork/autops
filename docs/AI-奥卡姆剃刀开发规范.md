# AI 奥卡姆剃刀开发规范

## 一、目的、范围与依据性质

本规范约束 Agent 在需求分析、功能设计、编码、重构和审核中控制不必要复杂度，适用于前端、后端、接口、数据模型、任务处理、配置及测试。与前后端开发约束共同执行；具体技术栈、分层、UI、安全、错误处理和授权要求仍按对应规范及项目配置执行。

奥卡姆剃刀常被概括为“如无必要，勿增实体”。其重要前提是其他相关条件相当；它是选择与论证原则，不能证明最简单方案一定正确，也没有规定软件应有多少文件、接口或功能。[1]

没有一份通用于全部软件开发的“完整奥卡姆剃刀标准”。本文件依据文末出版物、论文及工程文章，将简约性、必要复杂度、信息隐藏、安全机制和渐进设计综合为规则。下文的决策流程、表格与审核清单属于规范归纳，不冒充文献原文或行业统一标准。

## 二、核心原则与必要前提

**在满足已确认业务需求、正确性、安全性、数据一致性、兼容性及适用的性能和可靠性要求的候选方案中，优先选择不必要假设更少、概念与机制更少、整体理解和维护成本更低、容易验证及修改的方案。新增复杂度必须有可说明的用途和依据。**

执行顺序：

1. 明确用户任务、验收条件、适用规模和运行环境，以及必须维持的业务不变量和现有契约。
2. 先排除不能满足上述约束的方案，再比较其余方案的复杂度与总成本；不能以实现更短为由选择不满足约束的方案。
3. 区分问题固有的复杂度与实现附带的复杂度。真实的业务规则、并发冲突及权限边界需要被正确表达；重复状态、无用途抽象和额外协调应尽量消除。[2]
4. 说明必要机制如何满足需求，并通过适用的验证检查其效果。资料不足时先查代码、契约或已有指标；无法消除的关键歧义按项目要求澄清，不虚构规模、故障概率或收益。
5. 新证据出现后重新评估。复杂度判断有上下文，不把当前最简方案当作永久架构。

简约性是满足必要约束之后的选择依据。性能、可靠性等目标存在冲突时，应说明实际取舍；不得私自降低已确认要求。

## 三、如何判断复杂度

按整个用户流程和系统链路评估，不以局部代码行数、文件数、请求数、抽象层数或依赖数中的某一个指标代替判断。

| 维度 | 必须检查的问题 |
| --- | --- |
| 使用与认知 | 用户要理解多少概念、选项和步骤？开发者能否局部理解行为？ |
| 结构与变化 | 有多少职责、依赖和隐式约定？修改一条规则会牵连哪些位置？ |
| 数据与一致性 | 有几个权威来源和派生副本？需要多少同步、失效及事务协调？ |
| 运行与故障 | 增加多少网络往返、后台任务、部署单元及故障路径？ |
| 验证与维护 | 是否增加配置组合、测试场景、升级、清理和排障负担？ |
| 演进与撤销 | 以后补充或替换有多难？是否涉及不可逆数据变化或公开契约？ |

不要求为小改动编制打分模型。简单任务用几句话交代必要性即可；存在实质取舍时再比较可行方案，不设置没有依据的权重或阈值。

## 四、何时保持简洁，何时允许提前设计

- 默认实现当前已确认的完整需求。不得仅以“以后可能用到”为由添加功能、字段、状态、配置项、插件体系、通用框架、扩展点或依赖。[3][6][7]
- 需求不确定、反馈周期短、以后修改容易时，优先直接且可修改的实现，推迟尚未需要的能力。
- 保持清晰命名、合理职责、必要测试和可替换边界，不属于应当删去的未来功能。YAGNI 不授权忽略代码健康或让未来修改变得困难。[6]
- 对已知且推迟后代价明显上升的决策，可以提前处理；须说明变化依据、当前增加的复杂度及以后补充的代价。例如已确认的公开协议兼容要求和必须预先保护的数据。
- 需要提前处理某个边界时，只实现满足该边界的最小机制，不顺带建设整套尚无消费者的平台。
- 禁止为了“统一”新增仅包装一次调用、没有隔离变化或契约价值的中间层；项目明确要求的 API、Service、Repository 等既有分层仍须遵守。

## 五、何时保留冗余或增加保障

冗余是否合理取决于它承担的目标。额外机制有当前用途，并且收益能够覆盖一致性、故障和维护成本时，可以是必要设计。

| 类型 | 可成立的依据 | 必须交代的边界 |
| --- | --- | --- |
| 可靠性冗余，如备份、副本 | 明确的故障模型、恢复或可用性目标 | 失效检测、切换或恢复方式、验证方式及资源成本 |
| 数据冗余，如缓存、汇总 | 已知查询开销、负载或响应时间要求 | 权威来源、更新与失效、一致性要求、重建或清理 |
| 历史与审计 | 明确的追溯、恢复、任务查询或合规需求 | 消费者、保留范围与期限、访问权限、清理方式 |
| 重试与幂等 | 已知重复投递、瞬时故障及副作用风险 | 可重试条件、次数或时限、重复执行边界 |
| 适度代码重复 | 代码形似，但业务语义或变化原因独立 | 分别维护的理由，避免把同一业务规则复制成多个权威实现 |

- 不为假想的无限规模增加缓存、队列、分布式协调或多套数据源；也不能以当前规模小为由删除已知风险所需的保障。
- 不把代码重复、数据副本、容灾和未来功能预留混为同一种冗余。相同业务规则应集中维护；仅语法相似不足以证明应共用抽象。
- 安全领域的机制简洁原则与默认拒绝、完整访问检查同时成立；不得以简化为由移除适用的鉴权、输入校验或敏感数据保护。[5]
- 禁止以本规范作为自行新增降级、默认数据、备用数据源或失败兜底的授权；这些事项继续按项目既有确认要求执行。

## 六、何时拆分

拆分必须带来职责清晰、变化隔离、权限隔离或运行隔离等明确收益。优先围绕困难或可能变化的设计决策建立边界，隐藏内部实现；不能把每个处理步骤机械地变成一个模块。[4]

以下情况应评估拆分：

- 业务语义、变化原因、生命周期或权限要求独立。
- 一个模块同时掌握过多无关规则，理解、测试或修改其中一部分必须理解其他部分。
- 存在明确的耗时、资源、扩缩容或故障隔离要求。
- 相同技术细节分散在多处，改变协议、存储方式等决策会造成大范围修改。

拆分前必须说明新边界负责什么、输入输出是什么、隐藏哪项决策，以及是否增加事务、网络调用、部署或调度成本。优先在现有进程内按函数、组件或模块隔离职责；独立服务和异步化须有额外依据并遵循架构变更授权要求。

文件组织及项目已批准的长度门槛按前端规范和项目配置执行；不得仅为减少文件数合并独立职责，也不得仅为增加模块数进行机械切割。

## 七、何时合并、复用或聚合

以下情况应评估合并规则、抽取共用实现或聚合读取：

- 多处实现表达同一业务知识，并且修改同一规则时必须同步维护。
- 被拆开的部分必须共同维护同一不变量，额外接口和协调反而使正确性更难保证。
- 一个明确的用户任务被不必要地分散，产生反复切页、重复输入或多次确认。
- 一次读取固定需要多个细碎请求才能取得基本信息，且权限、数据量及更新频率允许聚合。

合并前必须检查：是否只是表面相似；是否因此耦合独立权限或生命周期；是否接入大量模式参数、条件分支、过量数据或过宽权限。合并若增加这些成本，应重新选择边界。

用户流程、页面、接口响应、代码模块、数据库表与部署单元是不同层面的边界。前端合并展示不要求后端合并职责；接口聚合返回不要求合并数据库表；模块拆分也不要求增加 HTTP 请求。

复用遵守现有前端“相同业务逻辑出现两次须抽取”等具体规则；不得将仅外观或语法相似误判为相同业务逻辑。聚合接口仍须遵守后端最小必要响应和字段权限要求。

## 八、Agent 执行流程与决策记录

### 设计前

1. 完整阅读本规范及前后端规范，定位源码、调用方、已有实现和相关验证。
2. 确认当前需求与硬约束，区分事实、已授权要求和尚未证实的设想。
3. 从复用既有能力的最小完整方案开始。仅在存在实质取舍时比较其他方案，说明必要性、总成本和以后修改的代价。
4. 对新增抽象、依赖、状态、配置、持久化副本、历史、任务或服务边界说明具体用途与维护责任；无法说明的增量不加入。

### 实施中

- 按已授权目标小步修改，保持现有契约和可读性；不因发现可精简之处就扩大范围或重写系统。
- 删除既有功能、历史数据、接口或字段前检查消费者、兼容性、保留义务及迁移影响，不能只凭当前页面未使用判断无用。
- 只保留必要状态；派生状态优先从权威来源计算，确需缓存或持久化时定义一致性。
- 性能优化以已知约束或测量为依据；不可把减少请求数当作唯一目标，也不可把复杂度从浏览器转移到数据库逐行查询。

### 完成后

- 依风险执行项目已有检查，验证正常、异常、边界及受影响契约；纯文档修改检查内容、路径与一致性。
- 说明采取的简化、保留的必要复杂度及理由，记录验证结果和未完成项；简单任务合并为简短说明，不额外生成重复决策文档。
- 架构调整、大规模重构、数据迁移或新增兜底按现有规则确认；常规已授权修改不因本规范增加一轮形式审批。

存在实质取舍时，使用以下简短记录即可，可放在实施说明中：

```text
目标与硬约束：用户任务、必须保持的性质及契约。
最小完整方案：复用什么，需要新增什么。
必要复杂度：具体需求或风险、依据、维护责任与验证方式。
边界选择：为何拆分、合并或保持现状；对调用方及一致性的影响。
暂缓内容：尚无依据的能力，以及何种实际条件出现时再评估。
```

## 九、审核清单

- [ ] 已确认需求、硬约束及受影响调用方，候选方案满足必要条件。
- [ ] 每项新增功能、机制、状态、配置、字段及依赖均有具体用途，没有凭空预留。
- [ ] 简化没有削弱权限、安全、正确性、一致性、兼容性或已确认的性能与可靠性要求。
- [ ] 已评估整个流程的使用、理解、运行、故障与维护成本，没有仅追求行数或数量更少。
- [ ] 拆分隔离了明确职责或变化；合并集中同一规则；无机械拆分、错误抽象及无依据的分布式化。
- [ ] 冗余、历史、缓存和重试有适用的生命周期、一致性或执行边界；新增兜底已按规定获准。
- [ ] 已复用既有能力，保留可修改性；未擅自接入依赖、架构变化或无关重构。
- [ ] 既有功能和数据的删改已检查授权与兼容影响，完成相关验证并如实报告未执行项。

## 十、参考文献与适用边界

以下文献的历史核对日期为 2026-10-15，各条“已核对”均为历史维护记录；2026-10-19 的工程资料调研未逐篇复核这些文献，不能据此更新其全文阅读状态。新增工程来源另见 [AI 编程工程实践参考](AI-编程工程实践参考.md)。优先使用原始论文、作者文章和官方工程指南；以下来源的权威范围不同，不能互相替代。未核对到的全文内容不作为强制条款依据。

1. **《Simplicity》**，*Stanford Encyclopedia of Philosophy*，2004 年首发、2022 年实质修订。[正文](https://plato.stanford.edu/entries/simplicity/)。已核对引言及第 2 节：简约原则具有“其他条件相当”的前提，实体种类少与表达简洁可能互相权衡；支持本规范的条件性定义，不提供软件架构的固定数量标准。
2. **Frederick P. Brooks Jr.，《No Silver Bullet: Essence and Accidents of Software Engineering》**，*Computer*，20(4)，10–19，1987。[DOI: 10.1109/MC.1987.1663532](https://doi.org/10.1109/MC.1987.1663532)；[公开全文](https://www.cgl.ucsf.edu/Outreach/pc204/NoSilverBullet)。依据其固有复杂度与附带复杂度的区分，不能推导为所有复杂性都可以删除。
3. **Niklaus Wirth，《A Plea for Lean Software》**，*Computer*，28(2)，64–68，1995。[DOI: 10.1109/2.348001](https://doi.org/10.1109/2.348001)；[公开论文副本](https://gwern.net/doc/cs/algorithm/1995-wirth.pdf)。依据其控制软件膨胀、审视规格和设计的主张，不据此强制追求最少代码行数。
4. **D. L. Parnas，《On the Criteria To Be Used in Decomposing Systems into Modules》**，*Communications of the ACM*，15(12)，1053–1058，1972。[DOI: 10.1145/361598.361623](https://doi.org/10.1145/361598.361623)；[公开重印正文](https://www.cs.lafayette.edu/~gexia/cs301/resources/parnas.html)。依据其信息隐藏、局部理解和隔离变化的模块划分标准；模块数量本身不代表设计质量。
5. **Jerome H. Saltzer、Michael D. Schroeder，《The Protection of Information in Computer Systems》**，*Proceedings of the IEEE*，63(9)，1278–1308，1975。[DOI: 10.1109/PROC.1975.9939](https://doi.org/10.1109/PROC.1975.9939)；[作者站点正文](https://web.mit.edu/saltzer/www/publications/protection/Basic.html)。其设计原则同时包括机制简洁、默认拒绝与完整访问检查，说明简约不能授权削弱安全。公开正文抓取受站点访问限制，原则核对采用公开可检索原文片段；不声称本次完整重读全文。

7. **Google Engineering Practices，《What to look for in a code review》**，[官方指南](https://google.github.io/eng-practices/review/reviewer/looking-for.html#complexity)。已核对正文：审核整体设计、可理解性、并发安全和过度设计，避免实现尚未需要的能力。它是 Google 工程实践，不自动覆盖目标项目的具体工具和测试要求。
8. **Anselm Blumer、Andrzej Ehrenfeucht、David Haussler、Manfred K. Warmuth，《Occam's Razor》**，*Information Processing Letters*，24(6)，377–380，1987。[DOI: 10.1016/0020-0190(87)90114-1](https://doi.org/10.1016/0020-0190(87)90114-1)；[出版方摘要](https://www.sciencedirect.com/science/article/abs/pii/0020019087901141)。原维护记录仅核对书目信息和摘要：在特定学习框架及条件下，讨论与观测一致的简短假设和可学习性。该结果属于计算学习理论，不能直接证明应用代码越短、组件越少或设计越简单就越正确；不据其摘要制定架构强制条款。
